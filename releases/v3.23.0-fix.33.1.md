## What v33.1 is

v33.1 is the batch after v33. It keeps the v33 provider and operator surface and adds a small set of opt-in or internal changes: an inert ad and tracker Blocker data port, one shared Docker entrypoint implementation, an updater that pages past releases it cannot install, a memory-sized `h3 auto` mode that is off by default, a one-call network token renewal with the old flow as fallback, a durable-head publication fix in the sn fork, and a design note for Stage B. The provider, updater and renewal paths change only where described below; everything else is opt-in, inert, or outside this repository's binaries.

## Highlights

- **Ad and tracker Blocker data, with a new pepper, and no caller.** The `connect` package gains the upstream Blocker subsystem and its generated host table: 163,972 host records in about 0.94 MiB of read-only data, hashed with a new 32-byte pepper. Nothing in the provider constructs or consults a Blocker, so runtime classification is unchanged. The CFAA table is unchanged from v33; the earlier 40,577 to 40,288 range refresh is already in that line, not in this batch.
- **One shared Docker entrypoint implementation.** `docker/scripts/provider_common.sh` holds the bootstrap, login and supervision logic. `start_stable.sh`, `start_jwt.sh` and `start_nightly.sh` become thin wrappers that select the mode and binary flavor. `BUILD`, `AUTH`, credentials, `TURBO` and `PELICAN` keep their existing behavior; the offline equivalence matrix matched the old scripts on those paths. Operator environment mapping is unchanged.
- **The updater never installs a release it cannot use.** `urnet-tools update` and the Docker update paths walk the release listing newest first, skip drafts, pre-release flags, pre-release tag names and releases without the provider tarball and its sha256 digest, and page up to ten pages of one hundred. An explicit `--tag` remains an operator override and is not filtered this way.
- **`h3 auto`: memory-sized fallback transports, off by default.** The new value for the `h3` control key sizes the proxied fallback set from the effective memory limit, with a 2 GiB floor, a 64-proxy ceiling and the existing pressure sweep as its only sensor. It never enables the beside-H1 auxiliary that `on` means. Without the key, behavior is unchanged.
- **Network token renewal in one call, with the old flow as fallback.** The provider tries `POST /auth/network-refresh` first and falls back to code-create and code-login when the server does not have the route or refuses the request. Transport errors, timeouts, rate limits and server failures stay errors, so a transient problem does not overwrite a working token.
- **A durable-head publication fix in the sn fork only.** The sn port keeps prepared bytes across a cancelled publication and abandons only an empty pending temporary. It is not part of this repository's binaries and does not change a v33 provider.
- **Stage B is design only.** `--adopt-legacy-provider-key` has a design note and no implementation in this batch. Plain `provide` and `auth-provide` keep their current identity behavior.

## Added

### `h3 auto`

`urnet-tools set h3 auto` makes the `h3` key size the fallback set for proxied identities from memory pressure. The direct identity keeps the `direct` policy. Capacity is one proxy slot per 64 MiB of the effective memory limit, zero below a 2 GiB limit, capped at 64. The target grows by 4 proxies per 30 s pressure sample while smoothed memory pressure is below 0.30, holds between 0.30 and 0.50, sheds to 16 at 0.50, and drops to direct-only at 0.75. A change re-ranks through the existing sticky ranking and relaunches only the proxies whose eligibility changed.

The setting is off by default. With the key unset, the new controller returns before reading a sensor, and the transport behavior is what v33 has. See [H3 Auto](../docs/H3-Auto.md).

### Network JWT renewal at `/auth/network-refresh`

The hourly renewal path now tries `POST /auth/network-refresh` with the current network token. A 404, 405, 501 or a non-transient 4xx refusal falls back to the existing three-step flow. A 408, 425, 429, a 5xx or a transport error stays an error and leaves the current token in place. A response carrying a client JWT is rejected. Both successful paths verify the new token against `/transfer/stats` before it is written to disk.

### Blocker data

The port brings `ip_blocker.go`, `ip_blocker_block.go`, the `blocker/` generator and its tests from upstream connect. The generated table has 163,972 host records and zero literal IP ranges. `NewBlockerWithDefaults` starts disabled, and no provider code calls it. The only cost is the read-only data in binaries that link the `connect` package.

## Changed

### Docker entrypoint consolidation

The three start scripts are now thin wrappers over `provider_common.sh`, which contains the shared directory, architecture, proxy, custom-network, identity-reporting, IP-checker, vnStat-warning, login and supervision paths. The per-mode authentication contracts stay separate: `USER_AUTH` and `PASSWORD` for stable and nightly, an auth code or positional JWT for the jwt path.

The entrypoint's `BUILD` and `AUTH` precedence is unchanged, including the conflict warning where an explicit `BUILD` wins. `AUTHCODE` and `URNETWORK_AUTH_CODE` remain aliases. `TURBO` and `PELICAN` keep their existing handling. The v33 operator variables still map through `provider_env.sh`, and with every one unset the container runs exactly `provide`.

### Updater release selection

The stable channel no longer trusts `releases/latest`. It walks `GET /releases` newest first, one hundred per page, up to ten pages, and takes the first release that is not a draft, not flagged as a pre-release, not named like a pre-release (`rc`, `alpha`, `beta`, `pre`, `preview`, `nightly`, `snapshot` or `dev` as a tag component), and publishes `urnetwork-provider-<tag>.tar.gz` with a sha256 digest. The same selector runs in the POSIX Docker update scripts. A tag passed with `--tag` is still an explicit operator override for a canary or a rollback.

## Fixed

### sn durable-head publication (sn fork only)

The sn fork's durable head now marks a publication before its bytes exist, writes the pending checkpoint only after the bytes are complete and synced, and treats the create marker as transient head metadata during restore and rebind. A cancelled publication whose bytes reached stable storage is recoverable. `Reconcile` abandons only a zero-byte pending temporary and refuses partial or tampered bytes. This fix lives on the sn fork's `fix/durablehead-cancel-window` branch and is not in this repository's provider binaries.

## Design only

### Stage B: `--adopt-legacy-provider-key`

The Stage B design note recommends an opt-in strict custody mode for a later release. It is not implemented here: there is no flag, no gate and no change to `provide` or `auth-provide`. The note covers the identity-destroying paths an adoption mode would have to close, including unreadable or corrupt client JWT stores, hot restart disabled, network mismatch, renewal verdicts, age pruning and revoked-identity eviction. Treat the design as input for review, not as shipped behavior.

## Status and verification

## Known limits

- The Blocker subsystem is present but inert. A future release that wires it to DNS or routing will need its own review.
- `h3 auto` is not a capacity guarantee: with no memory sensors it fails open to the memory-derived capacity.
- An explicit `--tag` bypasses the stable filter for a canary or rollback. That is deliberate, and it requires the operator to name the tag.
- Stage B changes nothing in this batch.
